# RFC #2 Implementation Plan — `streamline.colorBy`

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a `colorBy` option to the existing `mark: "streamline"` so a single spec can produce the per-direction-hued flow visualization the joy.html particle-flow demo renders today as canvas pixels.

**Architecture:** No new mark, no new data shape. One optional field on the streamline layer config: `colorBy: "angle" | "speed" | undefined`. When set, each streamline's stroke is computed from the velocity field at the seed via HSL mapping. When unset, current behavior (single-color from `theme.fg`) is preserved byte-stably.

**Tech Stack:** TypeScript, Zod, vitest, existing `expr-eval` evaluator. Zero new dependencies.

---

## Design — answers to obvious objections

**Q: Why not a new `mark: "particle-flow"`?**
A: 95 % of the code is identical. The visual difference is "color per polyline" — a render-time choice, not a structural one. Adding a mark would double the registry surface, double the schema surface, and force users who want both flavors to maintain two specs. One option flag is correct.

**Q: Why not also `colorBy: "step"` (gradient along the polyline)?**
A: SVG can do it via a multi-stop `<linearGradient>`, but that's a separate plumbing concern (defs sharing, gradient ID dedup). Out of scope for v1. File as follow-up if requested.

**Q: How does `colorBy` interact with `encoding.color`?**
A: `encoding.color` is a row-driven channel and the streamline mark doesn't bind rows the way bar/line do. They're orthogonal; `colorBy` always wins for the streamline mark. Document this in the schema JSDoc.

**Q: AUDIT-06 (color count > 8) will fire — is that a bug?**
A: No. A flow field's whole point is many colors. The audit will warn but not error. If it becomes noisy in practice, gate AUDIT-06 against marks that opt-in to many colors. Track separately.

**Q: Determinism?**
A: `colorBy: "angle"` computes hue from `Math.atan2(vy, vx)` at the seed. atan2 has the same libm-drift concern as sin/cos. We already clamp via `canonicalStringify` precision (the seed point is already rounded). HSL string output uses `.toFixed(1)` to stay byte-stable.

- [ ] **Step 3.2: Add the per-seed color computation in the compile loop.**

Right before `const stroke = theme.fg;` (currently line 325), replace with:

```ts
const defaultStroke = theme.fg;
const evaluator: Evaluator = defaultEvaluator;
const seeds = generateSeeds(cfg, domain);

// ... preflight unchanged ...

// Track max speed across seeds so colorBy: "speed" normalizes well.
// Computed in one pre-pass; cheap (one evaluator call per seed).
let maxSpeed = 0;
if (cfg.colorBy === "speed") {
  for (const s of seeds) {
    const vx = safeEval(evaluator, cfg.dxdt, { x: s.x, y: s.y });
    const vy = safeEval(evaluator, cfg.dydt, { x: s.x, y: s.y });
    const sp = Math.hypot(vx, vy);
    if (Number.isFinite(sp) && sp > maxSpeed) maxSpeed = sp;
  }
  if (maxSpeed === 0) maxSpeed = 1; // avoid div-by-zero on still field
}

function strokeFor(seed: { x: number; y: number }): string {
  if (!cfg.colorBy) return defaultStroke;
  const vx = safeEval(evaluator, cfg.dxdt, { x: seed.x, y: seed.y });
  const vy = safeEval(evaluator, cfg.dydt, { x: seed.x, y: seed.y });
  if (!Number.isFinite(vx) || !Number.isFinite(vy)) return defaultStroke;
  if (cfg.colorBy === "angle") {
    const deg = ((Math.atan2(vy, vx) * 180) / Math.PI + 360) % 360;
    return `hsl(${deg.toFixed(1)},70%,55%)`;
  }
  // "speed"
  const sp = Math.hypot(vx, vy) / maxSpeed;
  const light = (30 + sp * 50).toFixed(1); // 30% .. 80% lightness
  return `hsl(210,70%,${light}%)`;
}
```
