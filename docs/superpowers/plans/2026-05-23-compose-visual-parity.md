# Compose Visual Parity Implementation Plan — close the gap to the hand-authored Life-in-Glyph heroes

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Extend Glyph's compose grammar from "minimal schematic primitives" to "every visual pattern any of the 8 Life-in-Glyph hand-authored heroes uses." After this lands, any new Draw-Me page can be authored as one compose JSON spec with the same visual richness as the current hand-authored versions, and the existing 8 heroes can optionally be re-implemented as compose specs that visually match within ±2% pixel diff.

**Architecture:** Add three new grammar layers on top of the existing compose foundation: (1) **decorative primitives** (starfield, gradient defs, pattern defs, glow halos, silhouette paths from raw `d` strings, glyph-icon library); (2) **advanced animations** (per-element delays/staggers, SVG `<animateMotion>` along path references, click-to-replay event triggers, `prefers-reduced-motion` respect); (3) **typography + theme depth** (per-mark font-family, per-mark fill overrides, extended palette of preset themes). Plus a **plugin registry** for one-off subject-specific marks (heart-icon, leopard-silhouette, etc.) so the schema enum doesn't bloat. Plus a **visual-parity verification suite** that pixel-diffs each compose hero against its hand-authored counterpart and fails CI if the diff exceeds 2%.

**Tech Stack:** TypeScript, Zod schemas, vitest (snapshot tests + new pixel-diff tests via `pixelmatch` + `sharp`), SVG (output), SMIL animations, CSS media queries embedded in SVG `<style>`.

**Total effort estimate:** 5 RFCs, ~35 tasks, ~1500 LOC across `packages/core/src`. Shipped as 5 separate PRs for incremental review.

## Sum of what's missing from compose

| Category | Hand-authored uses | Current compose has | Gap |
|----------|--------------------|--------------------|-----|
| Decorative circles | 37 starfield + halos | `circle` mark | starfield primitive + glow halos |
| Gradients (radial, linear) | Earth, Moon, heart, sunflower head | none | gradient defs + reference-by-id |
| SVG patterns (hatch) | cylinder, rotor body, deferent | none | pattern defs + reference-by-id |
| Complex silhouettes | leopard body, heart, sunflower petals, gear teeth, slider-crank | a few hard-coded marks | raw-`d`-string `silhouette-path` mark + a small icon library |
| Per-element delay/stagger | leopard spots, sunflower seeds | none | `delayMs` on animation + group `staggerMs` |
| `<animateMotion>` on a path | spacecraft, sweep dot, indicator dot, Moon pointer | none | new `motion-along-path` animation kind |
| JS-driven counters | Orion day, leopard step, sunflower seed | none | new `text-tick` mark or `<animate>` on text content |
| CSS keyframes (custom easing) | pendulum swing ease-in-out, heart sharp peak | basic SMIL only | richer SMIL with keyTimes + keySplines |
| `prefers-reduced-motion` | every page | none | wrap animations in `<style>@media …</style>` |
| Click-to-replay | every page | none | SVG event triggers (`begin="click"`) or doc-level JS |
| Multi-stop linear gradient on stroke | spacecraft path | none | covered by gradient defs above |
| Per-mark font-family / italic | all pages | partial | full font config in TextMarkSchema |
| Hatched ground / paper background | piston + clock | `gridPattern` only | pattern-based bg option |

**Conclusion: every gap maps to standard SVG features.** None of this requires new fundamental SVG capabilities; it's pure grammar extension.

`starfield.ts`:
```ts
import type { SceneMark } from "../../scenegraph/types.js";

export interface StarfieldCfg {
  count: number;
  seed: number;
  region: { x: number; y: number; w: number; h: number };
  radiusMin?: number;
  radiusMax?: number;
  twinkleMs?: number;  // 0 = no twinkle
  groups?: number;     // 1 or 2 — 2 groups have interleaved twinkle phases
}

/** Linear congruential generator (LCG) — deterministic, byte-stable.
 *  Modulus 2^31-1, multiplier 48271, increment 0. Standard "Park-Miller". */
function makeRng(seed: number): () => number {
  let state = seed >>> 0;
  return () => {
    state = (state * 48271) % 0x7fffffff;
    return state / 0x7fffffff;
  };
}

export function compileStarfield(cfg: StarfieldCfg): SceneMark[] {
  const rng = makeRng(cfg.seed);
  const rMin = cfg.radiusMin ?? 0.5;
  const rMax = cfg.radiusMax ?? 1.2;
  const out: SceneMark[] = [];
  for (let i = 0; i < cfg.count; i++) {
    const x = cfg.region.x + rng() * cfg.region.w;
    const y = cfg.region.y + rng() * cfg.region.h;
    const r = rMin + rng() * (rMax - rMin);
    out.push({ type: "circle", cx: x, cy: y, r, fill: i % 2 === 0 ? "#ffffff" : "#cbd5e1" });
  }
  return out;
}
```

// src/registry/marks.ts
import type { z } from "zod";
import type { SceneMark } from "../scenegraph/types.js";

interface CompositeMarkPlugin<TCfg> {
  schema: z.ZodType<TCfg>;
  compile: (cfg: TCfg, child: { at: { x: number; y: number }; size?: { w: number; h: number } }) => SceneMark[];
}

const registry = new Map<string, CompositeMarkPlugin<unknown>>();

export function registerCompositeMark<TCfg>(id: string, plugin: CompositeMarkPlugin<TCfg>): void {
  if (registry.has(id)) throw new Error(`mark "${id}" already registered`);
  registry.set(id, plugin as CompositeMarkPlugin<unknown>);
}

export function getCompositeMark(id: string): CompositeMarkPlugin<unknown> | undefined {
  return registry.get(id);
}
```

// __fixtures__/parity/lib/pixel-diff.ts
import sharp from "sharp";
import pixelmatch from "pixelmatch";

export async function pixelDiffSvgs(svgA: string, svgB: string, width = 800): Promise<number> {
  const [pngA, pngB] = await Promise.all([
    sharp(Buffer.from(svgA)).resize({ width }).png().raw().toBuffer({ resolveWithObject: true }),
    sharp(Buffer.from(svgB)).resize({ width }).png().raw().toBuffer({ resolveWithObject: true }),
  ]);
  if (pngA.info.width !== pngB.info.width || pngA.info.height !== pngB.info.height) {
    throw new Error(`dimensions differ: ${pngA.info.width}x${pngA.info.height} vs ${pngB.info.width}x${pngB.info.height}`);
  }
  const diff = pixelmatch(
    pngA.data, pngB.data,
    null,
    pngA.info.width, pngA.info.height,
    { threshold: 0.1 },
  );
  return diff / (pngA.info.width * pngA.info.height);
}
```

### Patch tasks (Tasks A–K)

**Task A — `<ellipse>`, `<polygon>`, `<polyline>` primitives**
Schema additions to ComposeChildSchema. Each compiles to its primitive SceneMark variant (ellipse, polygon, polyline). 50 LOC + 3 tests.

**Task B — `attribute-animate` animation kind**
Generic SMIL `<animate attributeName="…" values="…;…;…" dur="…s" repeatCount="indefinite" begin="…s"/>` for any attribute (opacity, r, cx, cy, fill, stroke, x, y, width, height). Schema:
```ts
{
  kind: "attribute-animate",
  attributeName: z.string().min(1).max(40),
  values: z.array(z.union([z.number(), z.string()])).min(2).max(50),
  durationMs: z.number().int().min(100).max(120_000),
  keyTimes: z.array(z.number().min(0).max(1)).optional(),
}
```
Used for Orion's `pulse-earth` (animates r), pulse-moon (animates r), and any future opacity flash / morph use case.

**Task C — Multi-keyframe easing for swing + pulse**
Extend existing LoopAnimationSchema's swing + pulse with optional `keyTimes` (number[]) + `keySplines` (string for cubic bezier control points like "0.42 0 0.58 1") arrays. When omitted, defaults to symmetric easeInOut (current behavior preserved). Heart-beat hero needs 5-point keyTimes "0;0.08;0.20;0.35;0.50;1.0" + matching keySplines for sharp peak.

**Task D — Document stroke-gradient (already works)**
Add to RFC #9 Task 1 docs: "GradientDefSchema works for both `fill: 'url(#…)'` and `stroke: 'url(#…)'` on any mark. No code change."

**Task E — Optional `id` on every mark**
Add `id: z.string().min(1).max(60).optional()` to ComposeChildSchema. compileChild propagates the id to the outermost SceneMark of the child's compilation. Renderer emits `id="…"` on the corresponding `<g>` wrapper. Enables `<animateMotion>`, `<mpath xlink:href>`, `<set href>`, and `<use href>` references.

**Task F — `<title>` + `<desc>` in compose-rendered SVG**
ComposeSpecSchema gains optional `description: z.string().max(500)`. Renderer emits `<title>${spec.title}</title><desc id="glyph-desc">${spec.description ?? "Glyph compose scene"}</desc>` inside the root `<svg>`. Mirrors existing chart-spec behavior.

**Task G — `raw-svg` SceneMark variant + raw-svg plugin mark**
For plugins (RFC #12) that need effects beyond the SceneMark primitive set — filters, masks, foreign objects, complex gradient stop chains. The mark's config is a single `xml: string` field with strict size cap (4 KB) and a regex allowlist for safe SVG element names (no `<script>`, no `<foreignObject>`, no `<image>`). Compiler trusts the string and emits it verbatim inside the group `<g>`.

**Task H — `fade-in-out`, `flash`, `morph` animation kinds**
Three more entries in LoopAnimationSchema:
- `fade-in-out`: SMIL `<animate attributeName="opacity" values="…" .../>`
- `flash`: same but sharp keyTimes "0;0.05;0.15;1" — used for lightning, alert blinks
- `morph`: `<animate attributeName="d" values="${dFrom};${dTo};${dFrom}" .../>` — used for path-shape interpolation
All compile to the same `attribute-animate` machinery from Task B; these are convenience sugar.

**Task I — `kinematic-keyframes` plugin pattern**
For mechanisms whose live state depends on a parameter (e.g. slider-crank rod endpoint as a function of crank angle), the plugin precomputes N keyframes of the dependent variable and emits an `attribute-animate` chain with those values. Example: a `slider-crank-anim` plugin takes `crankRadius`, `rodLength`, `cycleMs` and emits 36 keyframes for the rod endpoint's `x2` + `y2` attributes (one per 10° of crank rotation). The plugin is the right level — compose grammar doesn't need a generic "function-driven animation" primitive.

**Task J — Font pinning for parity tests**
Compose theme's `space-dark`, `pencil-parchment`, `life-organic` presets each declare a canonical `font-family` (e.g. `"Iowan Old Style", Georgia, serif` for pencil-parchment). The pixel-diff harness in Task 17 force-loads the same fonts via sharp's `text` rendering options OR uses a Web-safe fallback chain (Georgia is available on macOS, Windows, and rendered by sharp's default font config). Document this constraint in Task 17.

**Task K — `pathLength="1"` normalization for draw-in targets**
silhouette-path's schema gains optional `drawIn: { durationMs, easing }` field. When set, the renderer emits `pathLength="1"` on the path and adds a SMIL `<animate attributeName="stroke-dashoffset" from="1" to="0" dur="…s" .../>` with `stroke-dasharray="1"`. This normalizes the path's length to 1.0 so the draw-in works regardless of the actual path geometry.

### What's NOT in the plan (intentional)

- **WebGL or canvas-based effects.** All output is pure SVG. Future use cases needing GPU-accelerated effects (particle systems with > 1000 elements, real-time fluid sim) would need a different output target — out of scope for this plan.
- **Foreign-object HTML embed** (`<foreignObject>`). Rejected for security (HTML inside SVG opens XSS surface) and portability (some viewers don't support it).
- **Live JS evaluation inside the SVG.** All animations are declarative (SMIL or CSS). No runtime JavaScript in compose output. Trade-off: kinematic chains (slider-crank rod) compile to N precomputed keyframes instead of live formulas. Acceptable for visualization quality at typical frame rates.
- **Editing the hand-authored heroes in place.** The plan ships compose-v2 specs ALONGSIDE the existing hand-authored heroes. Once parity tests pass (Task 18), the page CAN be flipped to use the compose-rendered SVG, but flipping is a separate decision per hero. Some pages may keep the hand-authored version for fine-grained author control over CSS keyframe interpolation (which SMIL approximates but doesn't perfectly match).

### Risk inventory

| Risk | Mitigation |
|------|------------|
| Cross-platform font rendering causes parity tests to fail | Task J pins canonical fonts per theme + uses a fallback chain that resolves identically across the CI matrix |
| Plugin registry's `unknown` config type sacrifices Zod safety | Each plugin declares its own Zod schema; the registry validates against it before dispatching |
| SMIL animations aren't pixel-identical to CSS keyframes (subtle easing differences) | Parity tests snapshot at t=0 to bypass timing-dependent diffs; the 2% threshold absorbs minor easing-curve differences |
| Slider-crank kinematic plugin produces a large SVG (36+ keyframes × multiple attributes) | Acceptable; the SVG is still tiny (~3 KB) and byte-locked |
| Visual style drift if hand-authored CSS uses computed colors / variables | Compose theme presets pin exact hex values; bg/fg/accent tokens explicit |
| Pixel-diff harness adds two devDeps (`pixelmatch`, `sharp`) | Both are widely-used Node libs; sharp is already common in Node SVG tooling |

### After all 5 RFCs land

The compose grammar will be able to express:
- Every existing Life-in-Glyph hero at < 2% pixel diff
- Any new "Draw Me X" page where X is a finite set of recognizable visual elements (subject silhouette, decorations, data plot, animations)
- Future schematic visualizations (engineering diagrams, biological cycles, geological cross-sections) via the plugin pattern

The compose grammar will NOT be able to express:
- Particle systems with > 1000 entities (use canvas/WebGL for those)
- Live interactive sims that require runtime physics solvers (e.g. continuous gravity simulation; the compose path uses precomputed keyframes)
- Real-time data streams (compose is deterministic; live data needs the chart-spec path)

These are deliberate boundaries; the compose path is for **deterministic, byte-stable, agent-authorable visualizations**, not for arbitrary interactive UI.
